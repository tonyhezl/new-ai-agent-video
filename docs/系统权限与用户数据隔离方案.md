# 系统权限与用户数据隔离方案

## 1. 背景与目标

当前系统已经具备登录、Token、用户角色和团队成员的基础能力，但权限粒度主要停留在 `admin/user`，项目、剧本、分镜、资产和生成任务之间没有统一的资源访问校验。前端菜单也主要依赖本地静态配置，隐藏菜单不能构成安全边界。

本方案的目标是建立一套可普遍复用的“功能权限 + 资源权限 + 数据范围”模型：

1. 可以由管理员控制目录、页面、按钮和 API 权限。
2. 用户只能看到并操作自己有权访问的项目及其子资源。
3. 个人资源、团队资源和项目成员权限可以共存，并支持后续多团队扩展。
4. 所有权限在后端落地，前端菜单只负责体验，不承担安全职责。
5. 兼容当前无状态 Token、现有 `admin/user` 角色和单团队部署，采用分阶段迁移，避免一次性重构。

本文最初用于定义改造方案。当前实现状态和验收结果见第 14 节；前文保留设计依据，便于后续模块按同一规则接入。

## 2. 当前系统权限现状

### 2.1 认证与登录态

后端采用 Spring Security 无状态认证：

- `TokenAuthenticationFilter` 从 `Authorization` 或 `access_token` 读取令牌。
- Redis 保存 access token 和 refresh token。
- `SecurityUserDetails` 携带 `userId`、`username`、`currentTeamId` 和 authorities。
- `SecurityConfig` 默认要求请求已认证，登录、注册、刷新、Swagger 和部分媒体路径放行。
- 开启了 `@EnableMethodSecurity`，已有接口可以使用 `@PreAuthorize`。

### 2.2 角色与团队

系统已有 `sys_user`、`sys_role`、`sys_user_role`，当前常用角色为 `admin` 和 `user`。`UserService` 已支持查询、分配和移除角色，若干系统配置接口使用 `hasRole('ADMIN')`。

团队侧已有 `afv_team`、`afv_team_member`，成员角色为创建者、管理员、普通成员。Token 中已经保存当前团队 ID，但 `TeamService.createTeam()` 仍限制单团队，注册用户也会自动加入默认团队，因此目前更接近单租户部署。

### 2.3 前端菜单

`ai--agent-video-web/components/dashboard/sidebar-nav.tsx` 根据当前用户是否包含 `admin` 决定是否显示管理员设置项。菜单、路由和按钮权限没有从后端下发，也没有统一的路由守卫或按钮级权限组件。

因此，用户即使看不到菜单，仍可能直接调用 API；任何关键接口都不能把前端隐藏作为授权依据。

## 3. 当前问题与风险

以下问题应作为 P0/P1 封堵项处理：

### 3.1 项目资源未统一隔离

- `ProjectService.page()` 直接分页查询，未按当前用户、团队或项目成员过滤，可能返回全量项目。
- `ProjectController.get(id)` 只判断项目存在，没有统一的访问校验。
- 项目更新、删除只按 ID 操作，没有确认调用者是否为所有者、项目成员或团队管理员。
- 项目成员增删接口没有充分校验操作者权限。

### 3.2 子资源可能通过 ID 越权

剧本、分集、场次、分镜、镜头、场景状态、资产及资产子项等接口，不能只校验自身 ID 是否存在，必须沿父级资源回溯到项目并校验项目访问权。否则用户可以猜测 ID 读取或修改其他用户的数据。

重点覆盖：

```text
镜头 -> 分镜集 -> 分镜 -> 项目
场次/剧本 -> 分集 -> 剧本 -> 项目
资产子项 -> 资产 -> 项目
生图/生视频任务 -> 所属项目或任务创建者
POV 镜头/音频 -> POV 故事 -> 用户或项目
```

### 3.3 资产、媒体和生成任务接口不一致

资产详情、项目资产列表、更新和删除路径没有统一调用资源权限方法；媒体库批量清除不能信任前端传入的记录或 URL，必须逐条重新验证归属。生图、生视频任务的分页接口虽有按用户查询的实现，但单任务详情和任务子项查询仍应显式校验用户、项目或团队范围。

### 3.4 媒体路径可能绕过业务鉴权

`SecurityConfig` 对 `/media/**` 放行。公开媒体和私有媒体必须区分：私有文件不能仅凭可猜测 URL 读取，建议改为短时效签名 URL，或由受保护接口代理下载。

### 3.5 角色、团队角色和数据范围没有统一

系统角色、团队成员角色、项目成员角色目前没有统一映射。`admin/user` 可以保留作为兼容角色，但新功能不应继续把所有能力压缩为一个管理员判断。

## 4. 目标权限模型

采用 **RBAC + 资源级 ABAC/Scope** 的组合模型：

- RBAC（Role Based Access Control）：决定用户能使用哪些功能、菜单、按钮和 API。
- 资源授权（Resource Authorization）：决定用户能否访问某个团队、项目或子资源。
- 数据范围（Data Scope）：决定列表查询返回个人、团队、项目成员范围还是全量。

### 4.1 权限主体和边界

```text
用户 User
  -> 系统角色 System Role（功能权限）
  -> 团队成员 Team Member（团队范围和团队角色）
  -> 项目成员 Project Member（项目范围和项目角色）
  -> 资源 Resource（项目、剧本、镜头、资产、任务、媒体）
```

任何资源操作都需要同时满足：

```text
已登录
AND 拥有功能权限码
AND 通过资源归属/成员关系校验
AND 操作符合数据范围和动作（查看、编辑、删除、管理）
```

### 4.2 建议内置角色

系统角色（跨团队的后台能力）：

- `SUPER_ADMIN`：平台所有权限，仅限极少数运维账号。
- `SYSTEM_ADMIN`：用户、角色、菜单、模型、存储和系统配置管理。
- `MEMBER`：普通登录用户的基础功能。

团队/项目角色：

- `TEAM_OWNER`：团队所有者，可管理成员、团队设置和全部团队项目。
- `TEAM_ADMIN`：团队管理员，可管理团队成员和项目，但不能转移所有者。
- `PROJECT_OWNER`：项目所有者，可管理项目成员和项目全部内容。
- `PROJECT_EDITOR`：可编辑项目内容，不能删除项目或管理敏感设置。
- `PROJECT_VIEWER`：只读查看项目及允许查看的生成结果。

`admin/user` 继续映射到 `SYSTEM_ADMIN/MEMBER`，保证旧账号和旧接口平滑迁移。

## 5. 菜单、页面、按钮和 API 权限

### 5.1 菜单数据模型

新增系统菜单表（建议命名 `sys_menu`），统一存目录、页面、按钮和 API 权限声明：

| 字段 | 说明 |
| --- | --- |
| `id` | 菜单主键 |
| `parent_id` | 父级目录 |
| `type` | `DIRECTORY`、`PAGE`、`BUTTON`、`API` |
| `name` | 稳定标识，不随显示文案变化 |
| `title` | 前端显示名称 |
| `path` | 前端路由或 API 路径 |
| `component` | 页面组件标识，可为空 |
| `permission_code` | 如 `project:update` |
| `icon` | 图标名称 |
| `sort` | 排序 |
| `visible` | 是否显示 |
| `status` | 启用/禁用 |
| `created_at/updated_at` | 审计字段 |

新增 `sys_role_menu` 关联角色和菜单。若后续需要更细的数据范围，可增加 `sys_role_data_scope`，不要把范围逻辑硬编码到菜单表。

### 5.2 权限码命名

推荐采用 `资源:动作`，必要时增加范围后缀：

```text
dashboard:view
project:view
project:create
project:update
project:delete
project:member:manage
script:view
script:edit
storyboard:view
storyboard:generate
asset:view
asset:edit
asset:delete
generation:view
generation:create
media:read
media:delete
system:user:manage
system:role:manage
system:menu:manage
system:config:manage
pov:story:view
pov:story:edit
pov:voice:generate
```

权限码应在后端定义常量或枚举，菜单初始化数据和 Controller 注解引用同一份标识，避免字符串漂移。

### 5.3 登录后的权限接口

提供统一接口：

```text
GET /api/auth/permissions
```

返回当前用户、当前团队、角色、权限码、可见菜单、数据范围和权限版本：

```json
{
  "user": {"id": 1, "roles": ["TEAM_ADMIN"], "teamId": 2},
  "permissions": ["project:view", "project:update"],
  "menus": [{"name": "projects", "title": "项目", "path": "/projects", "children": []}],
  "dataScope": {"project": "TEAM", "asset": "PROJECT"},
  "permissionVersion": 12
}
```

前端启动、刷新 Token、切换团队和收到权限版本变化时重新拉取。侧栏按 `menus` 渲染，页面内用 `usePermission()` 或 `Can` 组件控制按钮；路由进入时再次判断页面权限，403 统一进入无权限页。前端控制只改善体验，后端必须独立拒绝未授权请求。

### 5.4 按当前业务模块分配权限

支持按模块分配，但必须把“模块功能权限”和“资源数据范围”拆开。模块权限解决“能不能使用某类功能”，资源范围解决“能操作哪一个项目或团队”。例如，用户可以拥有分镜生成权限，但只对项目 A 有编辑权；不能因为拥有 `storyboard:generate` 就访问其他用户的分镜。

建议建立稳定的 `module_code`，与前端路由和后端权限码一一对应：

| 模块编码 | 当前模块 | 示例权限 |
| --- | --- | --- |
| `dashboard` | 工作台 | `dashboard:view` |
| `project` | 项目 | `project:view/create/update/delete` |
| `team` | 团队与成员 | `team:view/member:manage` |
| `asset` | 资产库 | `asset:view/create/update/delete` |
| `script` | 剧本 | `script:view/edit/generate` |
| `storyboard` | 分镜 | `storyboard:view/edit/generate/compose` |
| `generation` | 生图、生视频、配音任务 | `generation:view/create/cancel` |
| `media` | 媒体库 | `media:read/delete` |
| `pov` | 第一人称猎奇故事 | `pov:story:view/edit`、`pov:voice:generate` |
| `system` | 用户、角色、菜单和系统配置 | `system:user/role/menu/config:manage` |
| `ai-config` | AI 模型、API、存储和能力规则 | `ai:model/config:manage` |

角色可以绑定多个模块和动作；用户再把角色绑定到具体作用域。建议新增作用域角色分配表，而不是把所有角色都写入现有全局 `sys_user_role`：

```text
sys_role_assignment
  id
  user_id
  role_id
  scope_type   SYSTEM / TEAM / PROJECT
  scope_id     SYSTEM 为 NULL，TEAM/PROJECT 为对应 ID
  status       ACTIVE / DISABLED
  expires_at   可选，临时授权
  created_by
  created_at/updated_at
```

权限计算规则为：

```text
有效权限 = 系统角色权限
         ∪ 当前团队作用域角色权限
         ∪ 当前项目作用域角色权限
```

其中项目作用域只能缩小资源范围，不能绕过项目父级授权；如需临时禁止某个动作，应增加明确的拒绝规则或撤销角色，不能依赖前端隐藏。管理员界面应支持“用户/角色 + 作用域 + 模块 + 动作”的组合配置，例如：

```text
张三 | 项目 A | PROJECT_EDITOR | script:view/edit
张三 | 项目 A | PROJECT_VIEWER | storyboard:view
李四 | 团队 B | TEAM_ADMIN      | project:view/create、team:member:manage
王五 | 系统   | SYSTEM_ADMIN   | system:user/role/menu:manage
```

这样即可按当前模块单独授予查看、编辑、生成、删除等动作，不必给用户整个系统管理员权限。

## 6. 用户、团队和项目的数据隔离

### 6.1 资源归属规则

每类资源明确一个父级授权边界：

| 资源 | 授权依据 |
| --- | --- |
| 个人项目 | `owner_id`，以及显式项目成员 |
| 团队项目 | `team_id` + 团队成员 + 项目成员角色 |
| 剧本/分镜/场景/镜头 | 所属项目的访问权 |
| 资产/资产子项 | 所属项目的访问权；公共资产需单独标记 |
| 生图/生视频任务 | 所属项目或任务创建者；结果继承父资源权限 |
| POV 故事 | 默认 `user_id` 私有；绑定项目后继承项目权限 |
| 媒体文件 | 媒体记录所属资源的权限；公开文件使用显式 `PUBLIC` 标记 |

客户端传入的 `userId`、`ownerId`、`teamId` 不能作为授权依据。服务端应从登录态、当前团队和父级资源推导或覆盖这些字段。

现有代码适配时不要机械新增同名字段：项目实体当前使用 `ownerType/ownerId` 表示个人或团队所有者，项目成员角色使用整数值，团队成员也有自己的角色枚举。授权服务应先封装这些现有字段，再逐步迁移数据库；`ownerType/ownerId` 与 `team_id` 不允许同时出现互相矛盾的事实来源。建议以现有字段作为兼容读模型，以统一授权服务作为唯一写入入口。

POV 故事当前以 `user_id` 为主要归属，项目绑定可能为空。应增加明确的 `visibility` 或 `share_scope`（`PRIVATE`、`PROJECT`、`TEAM`），未绑定项目时默认仅创建者可见，绑定项目后才继承项目成员权限，不能仅因为当前团队相同就自动公开。

### 6.2 数据范围

统一定义：

- `SELF`：仅本人创建或拥有的资源。
- `TEAM`：当前团队资源。
- `PROJECT`：当前用户是项目成员的资源。
- `ALL`：平台管理员范围，仅系统后台使用。

无当前团队时只能访问个人资源；切换团队后，列表和详情都必须使用新的团队上下文，旧团队 ID 不能继续生效。

### 6.3 查询和写入原则

1. 列表必须在 SQL/Mapper 层带上 owner、team、member scope 条件，禁止先查全量再在 Java 过滤。
2. 单 ID 查询先加载父级关系，再调用统一授权服务。
3. 写入时由服务端设置 owner/team/project，不接受客户端覆盖。
4. 删除、批量操作和导出必须逐项做权限校验，并使用事务。
5. 软删除资源也必须保留归属信息，防止通过历史 ID 访问。

## 7. 后端实现方案

### 7.1 统一授权服务

建议在 `security` 包新增：

```text
AuthorizationService
PermissionService
ResourceAccessService
DataScope
AccessAction
PermissionCodes
```

最小接口：

```java
boolean hasPermission(Long userId, String permissionCode);
boolean canAccessTeam(Long userId, Long teamId);
boolean canAccessProject(Long userId, Long projectId);
boolean canEditProject(Long userId, Long projectId);
boolean canDeleteProject(Long userId, Long projectId);
boolean canAccessAsset(Long userId, Long assetId);
void requirePermission(String permissionCode);
void requireProjectAccess(Long projectId, AccessAction action);
```

Controller 负责通用功能权限，例如：

```java
@PreAuthorize("@permissionService.has('project:view')")
```

Service 负责资源级校验，例如：

```java
authorizationService.requireProjectAccess(projectId, AccessAction.EDIT);
```

这样可以避免只保护 Controller 而被其他调用入口绕过，也避免每个业务 Service 各自复制一套判断。

### 7.2 关键接口封堵顺序

第一批优先改造：

1. 项目列表、详情、创建、更新、删除和成员管理。
2. 剧本、分集、场次、分镜、镜头、场景状态的所有读写接口。
3. 资产详情、项目资产列表、更新、删除和资产子项。
4. 生图/生视频任务详情、任务子项和结果媒体。
5. 媒体列表、批量清除、下载和公开链接。
6. POV 故事、角色参考音频、镜头和视频任务。

### 7.3 媒体访问

将媒体分成三类：

- `PRIVATE`：默认类型，必须通过业务鉴权后返回短时效签名 URL。
- `TEAM`/`PROJECT`：签名生成前验证对应团队或项目权限。
- `PUBLIC`：仅对明确标记为公开的结果放行。

不建议继续对整个 `/media/**` 使用 `permitAll`。迁移期间可保留兼容开关，但新文件必须走私有策略，并记录访问审计。

### 7.4 权限缓存与失效

权限查询可以缓存，但必须有明确失效机制：

- 用户角色、角色菜单、团队成员或项目成员变化时递增 `permission_version`。
- Redis 缓存键包含 `userId + teamId + permissionVersion`。
- `/api/auth/permissions` 返回版本号。
- 权限撤销后删除用户权限缓存，并使旧 Token/session 失效或在过滤器中拒绝旧版本。
- 对删除、系统配置等高风险操作不依赖长时间缓存。

### 7.5 异步任务、SSE 和外部文件的边界

生图、生视频、配音、POV 生成和合成任务可能在请求结束后由队列消费者或 SSE 回调继续执行。提交任务时必须保存 `created_by、team_id、project_id、resource_type、resource_id` 快照；消费者写入结果前重新检查父资源未删除且授权范围仍有效。任务查询、取消、重试、SSE 重连和任务流状态接口也必须按任务归属校验，不能只凭 `taskId`。

对象存储 URL、上传回调、下载链接和缩略图接口同样属于资源访问面。不能把数据库中保存的 URL 当成公开地址；应由媒体服务根据资源权限生成短期签名 URL，并限制签名用途、过期时间和下载范围。

### 7.6 配额、敏感配置和系统资源

AI API Key、模型配置、存储配置、能力规则、系统配置和用户管理属于 `SYSTEM` 范围，不应因用户拥有某个创作模块权限而自动可见。生图、生视频、配音等高成本操作还应预留团队/用户配额策略（查看配额、消耗配额、管理员调整配额），避免只做功能鉴权而没有成本隔离。

## 8. 数据库设计建议

现有表继续保留，在其上增量增加：

```text
sys_menu
sys_role_menu
sys_role_assignment
sys_permission_audit（可选，权限变更审计）
```

业务表统一检查并补齐以下字段（已有则复用）：

```text
owner_id       个人所有者
team_id        所属团队，可为空表示个人资源
project_id     所属项目
created_by     创建者
deleted_at     软删除时间
```

关键索引：

```text
(team_id, deleted_at)
(owner_id, deleted_at)
(project_id, deleted_at)
(user_id, task_id)
```

项目成员表应至少有 `project_id、user_id、role、status、created_at` 唯一约束；团队成员表应有 `team_id、user_id` 唯一约束和禁用状态。

`sys_user_role` 保留为系统级兼容关系；新的团队级、项目级授权使用 `sys_role_assignment`。角色菜单关系应增加唯一约束（`role_id、menu_id`），作用域角色关系应增加唯一约束（`user_id、role_id、scope_type、scope_id`），并对 `status`、`expires_at` 建索引。

## 9. 兼容与迁移计划

不建议一次性替换全部 Controller。按以下阶段交付：

### P0：先封堵越权

- 项目和项目成员接口补充资源校验。
- 所有剧本/分镜/资产/任务接口沿父级项目校验。
- 媒体批量删除逐条验证，私有媒体停止裸路径放行。
- 增加越权回归测试和安全日志。

### P1：统一授权内核

- 新建 `PermissionService`、`ResourceAccessService` 和动作枚举。
- 将重复的 admin 判断逐步迁移为权限码。
- 为旧 `admin/user` 建立角色映射，确保旧账号可继续使用。
- 增加 `sys_role_assignment`，让现有项目成员角色先映射为项目作用域角色；在映射完成前不得删除旧的成员角色字段。

### P2：菜单和按钮动态化

- 建表并初始化 `sys_menu`、`sys_role_menu`。
- 上线 `/api/auth/permissions`。
- 前端改为后端菜单 + `Can` 按钮控制。
- 增加路由守卫、403 页面和团队切换刷新。
- 管理端提供按用户/角色、作用域、模块、动作分配和回收权限的页面，并展示最终权限预览。

### P3：团队多租户和项目角色完善

- 去除单团队创建限制前，先补齐团队选择、成员邀请和跨团队测试。
- 明确个人项目与团队项目的可见性策略。
- 将团队角色映射到项目默认角色，但项目显式角色优先。

### P4：运营与审计

- 权限变更、成员变更、登录异常和高风险资源操作写入审计日志。
- 增加权限版本监控、缓存命中率和 403 统计。
- 定期扫描“无父级归属”“已删除仍可访问”等脏数据。

## 10. 验收测试矩阵

至少覆盖以下场景：

| 场景 | 期望结果 |

| 用户 A 查看用户 B 的项目列表 | 列表不出现 B 的项目 |
| 用户 A 用 ID 读取 B 的项目、剧本、镜头、资产、任务 | 返回 403 或统一的资源不存在，不泄露数据 |
| 团队成员查看团队项目 | 允许查看其有权限的资源 |
| `PROJECT_EDITOR` 修改项目 | 允许编辑，禁止删除和成员管理 |
| `PROJECT_VIEWER` 写入项目 | 返回 403 |

| 隐藏菜单后直接调用 API | 仍由后端返回 403 |
| 批量清除媒体包含他人记录 | 整体拒绝或只处理授权项，不能删除他人文件 |
| 切换团队后访问旧团队 ID | 返回 403，列表只显示新团队范围 |
| 禁用用户或团队成员 | 新请求不能继续访问受限资源 |

| POV 故事绑定项目后 | 继承项目权限；未绑定时仅创建者可见 |
| 同一用户只被授予 `script` 模块权限 | 可以进入剧本模块，但不能访问分镜、资产或系统配置 API |
| 用户在项目 A 有编辑权、项目 B 只有查看权 | A 可编辑，B 只能查看，两个项目的权限互不串用 |
| 临时角色过期或成员被禁用 | 新请求立即按失效状态拒绝，不依赖前端刷新 |
| 生成任务提交后撤销项目权限 | 已提交任务按策略继续或终止，但结果不可被无权限用户读取 |

测试应同时覆盖 Controller 直调、Service 调用、分页、详情、批量接口和异步任务回调，避免只测页面流程。

## 11. 安全边界与实施注意事项

- 前端菜单隐藏、按钮禁用和路由跳转都不是安全边界。
- 不要根据客户端传入的 `userId`、`teamId`、资源 URL 判断权限。
- 权限检查应在资源真正落库、读取、删除和生成任务提交前执行。
- 异步任务必须保存所属用户、团队和项目快照，回调写入时再次校验父资源状态。
- 统一返回 403/404 策略，避免通过错误差异枚举其他用户的资源 ID。
- 系统管理员权限应最小化分配，并对高风险操作启用二次确认或审计。
- 个人、团队、项目三种范围必须在产品和数据库层明确，不能以“当前团队为空”隐式推断为全量。

## 12. 复核结论与残余风险

### 12.1 与现有模块的兼容性

方案与当前模块边界是兼容的，推荐按以下方式落地：

- 项目、资产、剧本、分镜和媒体使用 `PROJECT` 资源边界，子资源统一向上追溯项目。
- 生图、生视频、配音使用 `GENERATION` 功能权限，但任务结果继续继承项目或 POV 故事权限。
- POV 保持独立模块，不强行并入剧本到视频链路；只有在显式绑定项目后才继承项目权限。
- 用户、角色、菜单、模型、API、存储和能力规则属于 `SYSTEM`，只允许系统级管理员访问。
- 工作台和公共预设可以有独立的只读权限，不能因为能看工作台就推导出项目数据权限。

### 12.2 仍需在实施前确认的风险

1. 现有项目采用 `ownerType/ownerId`，不能直接按方案中的 `owner_id/team_id` 双写，必须先确定唯一事实来源和迁移兼容层。
2. 现有 `sys_user_role` 是全局角色关系，无法表达“同一用户在项目 A 可编辑、项目 B 只读”，必须引入 `sys_role_assignment` 或等价的作用域授权表。
3. 现有项目成员和团队成员的整数/枚举角色需要定义到新角色的明确映射，不能只改显示名称。
4. “菜单可见”与“接口可调用”必须分别验收；动态菜单上线前，后端接口保护应先完成。
5. `/media/**`、文件上传回调、SSE 重连、异步消费者和外部任务回调必须纳入同一资源授权链，否则页面接口安全但文件或任务结果仍可能泄露。
6. 角色权限采用并集时没有显式拒绝规则；如果产品需要“允许大模块但禁止某个按钮”，应实现 deny 优先或更细粒度角色，而不能用前端隐藏替代。
7. 高成本 AI 操作还缺少配额和并发限制设计，应在生成权限之外增加团队/用户额度、幂等键和限流策略。
8. 权限缓存、Token 失效、团队切换和成员禁用需要约定生效时间，并用自动化测试验证，不能只依赖 Redis 删除缓存。

因此，本方案可以作为统一权限架构和模块分配的基线，但 P0/P1 的资源封堵、作用域角色表和旧字段映射完成前，不建议直接上线“管理员在页面自由配置权限”。

## 13. 结论

当前系统具备认证、基础角色和团队成员雏形，但还没有形成真正的菜单权限和用户数据隔离体系。推荐采用“权限码控制功能、统一授权服务控制资源、SQL 数据范围控制列表”的三层方案，先修复项目及其子资源的越权入口，再动态化菜单，最后完善多团队和审计能力。

该方案适用于剧本到视频创作链路、POV 猎奇模块以及后续新增业务模块：新模块只需声明权限码、资源父级和数据范围，即可复用同一套授权内核，不会把权限判断散落到各页面和各 Service 中。

### 14.3 对象存储边界

当前 S3 兼容存储模块的既有契约是返回公开桶或 CDN URL，连接测试也会验证该 URL 可以公网读取。公开 URL 一旦离开应用，应用内 RBAC 无法阻止访问，因此多用户隔离部署必须满足以下任一条件：

- 使用已完成资源级保护的本地存储；
- 对公开对象采用独立公开内容分级，确认其中不包含私有项目媒体；
- 后续升级为“媒体对象注册表 + 私有桶 + 受保护下载代理/短时签名 URL”，并同步改造生成模型读取本地参考资源的协议。

不能只把当前公开 URL 换成短时签名后继续写入业务表：签名过期会导致参考图、生视频和合成链路失效。该项属于对象存储协议升级，不应混入权限 Controller 改造中强行上线。
